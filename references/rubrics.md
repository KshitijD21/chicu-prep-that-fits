# Evidence-based coaching

These are coaching checklists, not validated hiring scores. For each observation quote the answer or confirmed project evidence. Mark missing, unclear or present; do not infer why it is missing. Rank fixes by relevance to the question, then evidence gap, then delivery polish. One useful fix is enough.

## Introduction

Check a clear current focus, one relevant real example and a connection to the role. Ask for a concise narrative rather than an entire biography. A duration target is a chosen drill goal, not measured duration. Do not rewrite a student's experience into credentials they do not have.

## Behavioral story

Check situation/context, task, specific personal action and actual outcome. STAR is an organizing aid. Ask what the student actually did when "we" obscures their role; collaborative language alone is not a fault. Outcomes can be qualitative (a bug was fixed before a demo, a teammate could use the tool). Ask for real numbers only if known. Never invent them or call an answer invalid solely because it has none. Follow-ups can ask about tradeoffs, learning, disagreement or what the student would change.

## Role-specific explanation

Software: problem, assumptions, approach, alternatives, tests and tradeoffs. Do not run a code judge or complete a graded assessment. Design: user need, decisions, constraints and evidence. Business/case: assumptions, reasoning, evidence and recommendation. Research: question, method, limitations and contribution. Other roles: agree on the interview format and use public requirements. Do not invent domain-specific correctness, certification or employer criteria.

## Ranked recommendation

Use this structure internally, send only its useful short version:

- Priority and concrete issue.
- Evidence: a short transcript quotation, source location or measured field.
- Why it affects this answer, stated without predicting hiring outcomes.
- One suggested change using only confirmed facts; use a visible placeholder/question for missing facts.
- One small drill.
- Observable recheck on take two.

Example: the answer names an action but no outcome. Quote the action as a strength, ask the student what happened next, then have them retell the story including that actual result. Recheck whether the result is explicit. Do not promise a score gain.

Progress is readiness for a **specific next practice step**, not a global offer-readiness score. If a take already answers the question clearly, acknowledge that and offer a follow-up rather than manufacturing a flaw.
